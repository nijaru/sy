# sy 0.5 state-of-the-art design audit

This note records the external design audit performed during the 0.5 clean-sheet rewrite. It is architectural guidance, not a requirement to preserve any 0.4 implementation.

The overall result is that the 0.5 architecture is on the right track. The audit mostly validated the existing design, while sharpening rooted-filesystem security, bidirectional reconciliation, compression policy, object-store capabilities, and benchmark requirements.

## Reference systems

The audit focused on mature systems whose constraints overlap a different part of `sy`:

- rsync 3.5.x: rolling delta, incremental recursion, exact delayed deletion, modern held-directory-FD path confinement.
- Unison: pairwise bidirectional synchronization against durable last-synchronized archive state, false-conflict elimination, staged updates.
- rclone bisync: history/listing safety, critical-error lockout and recovery, deletion/all-changed guards, checksum-based comparisons, namespace normalization.
- Syncthing: content block identities, conflict safety, case-collision handling, persistent multi-device state. Its distributed version-vector model is more machinery than a pairwise CLI synchronizer initially needs.
- Borg/restic/casync family: content-addressed/chunked storage, subprocess transport patterns, compression heuristics. CDC is valuable for persistent CAS/backup, not automatically the best one-shot SSH delta strategy.
- zstd/LZ4 upstream benchmarks: current compression-speed/ratio tradeoffs.

## Rooted filesystem security

### Decision

Use one secure held-directory-handle implementation as the normal Unix filesystem authority. Do not expose a user-facing insecure/fast resolver.

The portable model is:

1. resolve the operator-selected endpoint root once and hold its directory descriptor;
2. resolve peer-influenced components relative to held parent descriptors;
3. open every component with no-follow semantics;
4. perform leaf reads, stats, staging, rename, metadata mutation, and deletion using fd-relative operations;
5. cache held parent-directory descriptors so a directory walk is amortized across entries.

This matches the direction of current rsync security hardening. Final-component `O_NOFOLLOW` alone is insufficient because a raced parent symlink can redirect an otherwise-safe leaf operation.

Linux `openat2(RESOLVE_BENEATH, ...)` is not a separate user mode. It may be evaluated later as a transparent internal optimization only if:

- its semantics are proven equivalent to the portable resolver;
- seccomp/kernel availability cannot cause security-dependent fallback behavior;
- benchmarks show a meaningful improvement after parent-FD caching.

### Performance expectation

An uncached component walk costs approximately one directory `openat` per path component plus the leaf operation. Parent-FD caching changes the common many-files-per-directory case so directory traversal is paid once and each leaf operation remains essentially one fd-relative syscall.

For demand-driven signatures on large files, even the uncached walk is negligible beside reading and hashing the basis file. For huge small-file trees, benchmark the cached resolver before considering additional Linux-only machinery.

### Current implementation

`src/rooted_fs.rs` begins this boundary on Unix. It pins the root descriptor and opens regular files component-by-component with `openat(..., O_NOFOLLOW)`. Tests cover parent-symlink escapes, symlink leaves, and replacing the root pathname after its descriptor was pinned.

It is not yet the complete endpoint implementation. Scanner enumeration, staged writes, rename, metadata mutation, and deletion must move onto the same authority before remote filesystem mutation is considered fully confined. Windows needs an equivalent handle/reparse-point implementation before rooted content operations are advertised there; never fall back to unsafe path-join semantics.

## Bidirectional synchronization

### Existing 0.4 code is not a 0.5 foundation

The legacy classifier can miss real edits because it defines modification partly as `current_mtime > previous_mtime`; a same-size content change with preserved/equal/backward mtime can be missed. It can also declare two current files equal from size + mtime without a content proof. The legacy executor buffers whole files and can advance state around partially failed action sets.

Do not patch these semantics incrementally. Replace them.

### Pairwise three-way model

For a two-replica CLI synchronizer, use a Unison-style common-ancestor model rather than Syncthing-style distributed version vectors.

For every path, durable state represents the last successfully synchronized semantic value plus the endpoint-specific observation identities recorded after that success.

A current side is classified relative to that baseline:

- absent vs baseline absent: unchanged;
- stable endpoint identity equal to the stored identity: unchanged cheaply;
- identity unavailable/different: candidate change, requiring an exact semantic value before treating it as a real modification;
- current strong value equal to baseline: false-positive metadata/identity churn, therefore unchanged;
- current strong value different from baseline: real change.

For regular files the canonical value includes BLAKE3 content identity. Entry kind, symlink target, and policy-selected metadata must also participate in the semantic value as appropriate. Size/mtime are discovery accelerators, never equality proofs.

When both sides changed:

- same current semantic value: converged false conflict, advance baseline after postcondition checks;
- different current values: conflict;
- modified vs deleted: conflict;
- both deleted: converged deletion.

The initial pure semantic core lives in `engine::bisync` and intentionally has no timestamp inputs.

### Conflict UX

Default conflict behavior must preserve both user values. Do not default to `newer wins`: wall clocks, timestamp precision, restored mtimes, and clock skew make that an unsafe authority rule.

A user may explicitly request deterministic winner policies, but conflict-preserving rename/copy is the safe default.

### Snapshot and commit protocol

A bisync run should be:

1. acquire a durable pair lock;
2. load a trusted baseline generation;
3. take bounded ordered snapshots of both replicas before mutation;
4. preflight namespace/case/normalization collisions and destructive thresholds;
5. classify both sides against baseline, lazily requesting strong values only where identities cannot decide;
6. build the complete semantic action plan;
7. execute through the normal staged/verified engine;
8. validate source identities/postconditions for every affected path;
9. atomically commit the next baseline generation only for verified successful postconditions.

A critical copy/delete/state error must not optimistically advance history. Preserve the previous trustworthy generation and mark the pair recovery-required/locked out until a deliberate recovery/resync establishes a new baseline.

Resync should default to a preserve/superset-safe reconciliation and preview destructive choices; it must not silently choose one replica by timestamp.

### State requirements

The final bisync state format must support:

- non-UTF8/native namespace identity;
- pair identity without lossy path hashing;
- generation/version and policy fingerprint;
- common canonical value identity;
- per-side endpoint observation identity;
- endpoint timestamp precision/namespace semantics used when the generation was created;
- atomic generation commit plus recovery marker/journal;
- bounded/streamable loading for large trees.

Do not choose a database merely because the 0.4 tree already depends on one. Evaluate persistence after the semantic core is stable; the current legacy `fjall` dependency is not architectural guidance.

## Compression

### Previous benchmark is not authoritative

The old benchmark's `random` corpus was `(index % 256)`, which is highly structured and compressible. Several old comments also quote unrealistic multi-GB/s numbers as if they were universal end-to-end results, and the 0.4 256 MiB compression cutoff existed only because the old protocol buffered whole compressed files.

Protocol v3 streams bounded chunks, so those conclusions and limits do not carry forward.

### Likely final algorithm set

Prefer negotiating `none` and `zstd` initially. Do not retain LZ4 in v3 solely because the legacy dependency exists.

Current upstream benchmarks show zstd fast modes close to LZ4 compression throughput while retaining a better ratio. `none` is the correct second Pareto point for high-speed links and high-entropy/already-compressed data. LZ4 should be added only if `sy`'s own v3 benchmarks demonstrate a material workload where it improves total transfer time beyond both zstd-fast and none.

User-facing default: `compression=auto`.

Auto policy should eventually consider:

- negotiated algorithm support;
- actual chunk/file sample compressibility;
- observed/estimated link throughput and CPU pressure;
- minimum savings after frame overhead;
- known already-compressed formats only as a cheap hint, not the sole classifier.

Compression applies only to literal/full-file data chunks. Never compress copy instructions or signature records. Set `COMPRESSED` only when the encoded payload is actually smaller enough to earn its CPU/framing cost.

### Benchmark matrix

`benches/compress_bench.rs` now targets v3-sized chunks and must be used before selecting the production zstd profile. Benchmark at least:

- zstd fast/negative levels (`-5`, `-3`, `-1`), levels `1` and `3`;
- LZ4 as a challenger;
- source/log text, repetitive, mixed, and real high-entropy data;
- 64 KiB, 256 KiB, and 1 MiB chunks;
- compression and decompression throughput plus ratio.

Then model/measure end-to-end transfer time over representative 100 Mbps, 1 Gbps, 2.5 Gbps, and 10 Gbps links. The best compressor is the one that minimizes total wall time under the scheduler, not the one with the highest isolated codec throughput.

## Rolling signatures and delta policy

The current target of roughly 4096 signatures/file, power-of-two blocks clamped to 4 KiB..1 MiB is a reasonable starting policy, not a settled constant.

Benchmark:

- file sizes from small-delta threshold through multi-GiB;
- append, prepend/insert, localized edits, random 1/10/50% edits, and full rewrites;
- bandwidth/RTT profiles;
- signature bytes/count, CPU, old-destination reads, and transferred literal bytes.

Do not replace one-shot SSH rolling delta with CDC by default. CDC becomes more attractive when an endpoint owns a persistent content-addressed block index, especially object/backup storage.

The planner should eventually model a generalized basis candidate rather than assuming the current destination path is the only reusable old content. Alternate local files/reflink bases or object-native range bases can be future candidates without changing reconciliation semantics.

## Object stores

Replace a broad `server_side_copy` assumption with capabilities closer to what backends actually expose:

- range read;
- multipart/staged write;
- server-side range copy;
- object composition;
- backend generation/version preconditions;
- checksum semantics only where the backend defines them strongly enough.

This can let an object endpoint construct a new object from old-object ranges plus new literals without downloading unchanged data through the client.

## Release/benchmark additions

Before 0.5 release, in addition to existing gates:

- fuzz/adversarial tests for rooted path resolution and rename/symlink races;
- benchmark held-dirfd resolver with parent-FD caching on many-small/deep-tree workloads;
- bisync property/model tests over all combinations of absent/create/modify/delete/type-change and crash/failure points;
- bisync tests where mtime is equal, moves backward, or changes without content;
- namespace collision tests (case and normalization) before mutation;
- compression Pareto benchmark on v3 chunks and representative network profiles;
- delta block-size matrix and end-to-end SSH benchmark;
- critical-error bisync recovery tests proving an uncertain run cannot advance trusted baseline state.
