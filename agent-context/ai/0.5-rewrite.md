# sy 0.5 rewrite context

This file is the canonical implementation context for the `v0.5-architecture` branch. Read `docs/architecture-0.5.md` first for the target design, then use this file for current state and sequencing.

## Direction

0.5 is a ground-up internal rewrite. Do not preserve 0.4 internals, wire compatibility, module structure, transport APIs, log strings, or tests that encode obsolete implementation details.

Preserve user-facing behavior only when it is useful and intentional. Data-safety semantics take precedence over compatibility.

The target is:

```text
EntryStream -> Reconciler -> SyncOp -> Planner -> WorkItem -> Scheduler
                                      |
                                      +-> Local / Remote / Object endpoint capabilities
```

One binary (`sy`) acts as client and private remote agent (`sy __serve`). `sy-remote` must disappear before 0.5.

## Required Rust guidance

Use the user's `nijaru/dotfiles` skills:

- `dot_agents/skills/rust-expert/SKILL.md` for all Rust/systems work.
- `dot_agents/skills/rust-cli/SKILL.md` when the CLI migration begins.

Important consequences:

- stay on the repository's existing runtime unless the architecture requires otherwise;
- bounded channels/backpressure;
- typed library errors and contextual application errors;
- no recoverable `unwrap()`;
- every unsafe block has a `// SAFETY:` invariant comment;
- run `cargo clippy --all-features --all-targets -- -D warnings`;
- use `cargo deny`, audit, and Miri where relevant;
- when the CLI is replaced, use the `usage-rs` facade rather than building new clap infrastructure.

The branch currently remains Edition 2021 while substantial legacy code still compiles. Moving to Edition 2024 is reasonable after the legacy stack is deleted and should be done as an explicit reviewed migration, not opportunistically.

## Pieces worth keeping / evolving

These branch components already express useful 0.5 ideas, although they may move modules or change types:

- `src/endpoint/io.rs`: streaming readers and transactional staged writers.
- `src/endpoint/local.rs`: same-directory staging, atomic regular/link replacement, demand-driven xattr/ACL/BSD metadata.
- `src/endpoint/local_scan.rs`: ordered bounded local scan concept.
- `src/endpoint/transfer.rs`: capability-driven native whole copy, reflink patch, sparse-copy, staged streaming strategies.
- `src/sync/reconcile.rs`: ordered merge reconciliation and bounded batches as a proof of concept.
- bounded Tokio wire queues added to the v2 SSH path prove the desired backpressure shape.

Treat these as source material, not APIs that must remain stable.

## Known problems to eliminate

### Split engines

`src/sync/session.rs` still dispatches local sync to the new reconciler while SSH uses the old `StreamingSync` v2 path. This split is the next major architectural problem. Remote endpoints must feed the same new reconciler.

### Legacy stacks

Before release, delete:

- `src/bin/sy-remote.rs`
- `src/transport/`
- old `src/streaming/` v2 once v3 is live
- old `SyncEngine<T: Transport>` in `src/sync/mod.rs`
- old `StrategyPlanner` in `src/sync/strategy.rs`
- `src/ssh/connect.rs` and the homegrown SSH config parser once external OpenSSH is live
- compatibility-only whole-tree scan APIs and duplicate state/stats representations

### Scanner metadata cost

The new ordered local scanner no longer reads xattrs/ACLs eagerly, but still computes sparse allocation, inode/link count, and macOS flags on every entry. The final `Entry` must be lean and driven by metadata needs. Sparse extents in particular are transfer-time work.

### Deletion

Current local reconciliation uses a Bloom filter. It is safe because false positives retain files, but the final design should be exact and still bounded. Implement an on-disk reverse-readable deletion journal and remove the Bloom dependency from the new engine.

### Type transitions

Current local reconciliation rejects entry-kind changes. The final engine needs a transactional replace operation using staged replacement plus a same-directory tombstone/rollback sequence.

### Source mutation

Current scanning and transfer can race source changes. Add a source identity token and validate the opened/completed source before committing an inconsistent snapshot.

### Protocol v2

Current v2 problems include:

- destination scan materializes a tree;
- it precomputes signatures for every sufficiently large destination file;
- block size is hardcoded to 4096 bytes;
- delta generation still materializes `Delta.ops`;
- paths are UTF-8 `String`s;
- path confinement is lexical and does not defeat preexisting symlink components;
- old receiver verification is only a post-rename size check;
- protocol and sync semantics are tightly coupled to generator/sender/receiver structs.

Do not fix these by extending v2. Build v3 separately and delete v2 after cutover.

## Remote design

Use the external OpenSSH executable as transport. Do not keep `ssh2` in the final dependency graph.

Remote process launch:

```text
ssh -T user@host sy __serve
```

Do not put the remote filesystem path on the command line. The binary handshake carries the root.

The remote agent must confine every operation to a held root directory handle. On Linux use `openat2`/`RESOLVE_BENEATH` style resolution; on macOS walk directory FDs with no-follow semantics. Lexical normalization alone is insufficient.

## Protocol v3

Create v3 under a new `src/protocol/` module. Do not mutate `streaming/protocol.rs` into v3.

First protocol milestone:

1. typed `ProtocolError`;
2. bounded frame header/decoder with hard payload limit;
3. stream IDs;
4. ClientHello/ServerHello negotiation;
5. capability bitset;
6. raw/portable relative wire path representation;
7. property/adversarial tests for truncation, unknown values, and oversized lengths.

Next milestones:

- ordered cheap metadata stream;
- same core reconciler consuming local/remote scans;
- on-demand adaptive signature streams;
- direct streaming `DeltaOp` production;
- staged remote reconstruction;
- BLAKE3 source/staged digest comparison before commit;
- multiplexed streams controlled by the scheduler.

## Scheduler

Do not use a single file-count semaphore as the final resource model. Scheduler budgets should account for:

- number of active files;
- bytes buffered/in flight;
- metadata concurrency;
- hashing/compression CPU concurrency;
- network frame/write pressure.

A 20 GiB transfer must not have the same memory/concurrency weight as a 4 KiB file.

## Remote bootstrap / issue #26

Issue #26 asks for statically linked musl releases. Do not respond to the issue unless the user explicitly asks later.

The request fits the new design well:

- one static `sy` binary can be copied to a remote and invoked as `sy __serve`;
- no separate `sy-remote` artifact;
- external OpenSSH removes libssh2/OpenSSL from the application's SSH implementation;
- target at least x86_64 and aarch64 Linux musl artifacts;
- release CI must verify the result is truly static.

Automatic bootstrap can follow protocol stabilization: try installed compatible `sy`, then upload/cache a trusted matching static agent only if needed.

## CLI direction

Do not spend significant time repairing clap/manpage infrastructure that will be deleted. Once the engine/protocol boundaries are stable, migrate the user CLI to `usage-rs` v6 per the user's `rust-cli` skill. Generated usage specs should become the source for help/manpages/completions.

Retain familiar rsync-like syntax where it is useful, but remove flags that are misleading, redundant, or incompatible with a coherent 0.5 implementation rather than carrying permanent compatibility debt.

## CI state at rewrite reset

At the start of this ground-up phase:

- Format: green.
- Clippy all-targets/all-features: green on the active branch before the next rewrite slice.
- Linux/macOS tests still include obsolete 0.4 implementation assertions. In particular `sync_delta::test_inplace_strategy_used_with_hard_links` expects an old strategy/log and should be replaced, not satisfied by reintroducing the old path.
- Cargo audit/deny are red due existing dependency advisories; removing legacy dependencies should solve much of this naturally. Known affected dependency lines included `crossbeam-epoch`, `h2`, and `quick-xml` through the old dependency graph.
- Manpage check is stale old clap-generated infrastructure; final fix belongs with the `usage-rs` migration rather than preserving the current generator indefinitely.

The goal before merging 0.5 is **all checks green**, not “green except baseline failures.”

## Implementation order

Work in this order unless a discovered correctness problem requires reprioritization:

1. Canonicalize architecture/context docs.
2. Introduce `src/engine/` domain types independent of legacy `sync::scanner::FileEntry` / `SyncTask`.
3. Add exact bounded deletion journal and new merge reconciler.
4. Add first-class scheduler/resource budgets.
5. Introduce `src/protocol/` v3 framing/handshake with strong bounded decoder tests.
6. Add external OpenSSH transport + same-binary `__serve` entrypoint.
7. Implement remote ordered metadata endpoint using v3 and feed it into the same reconciler.
8. Add on-demand signatures, adaptive blocks, and streaming delta ops.
9. Add default remote BLAKE3-before-commit integrity and root-handle path confinement.
10. Migrate remaining local functionality (transactional type replacement, source identity, metadata needs) into the new engine.
11. Delete v2/transport/ssh2/sy-remote/legacy SyncEngine and obsolete tests.
12. Migrate CLI to usage-rs, then Edition 2024 if the cleaned dependency/tooling baseline supports it.
13. Clean dependency graph (`cargo machete`), make audit/deny green, regenerate docs from usage spec.
14. Add musl release matrix/bootstrap support.
15. Run realistic cross-platform/integration/benchmark release gates.

## Definition of done

0.5 is not done while two architectures remain. The release should contain one coherent engine and one binary, with old internals physically removed from the repository and realistic CI/benchmarks demonstrating correctness, bounded resource use, and competitive performance.
