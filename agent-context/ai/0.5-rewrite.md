# sy 0.5 rewrite context

This file is the canonical implementation context for the `v0.5-architecture` branch. Read `docs/architecture-0.5.md` first for the target design, then use this file for current state and sequencing.

## Direction

0.5 is a ground-up internal rewrite. Do not preserve 0.4 internals, wire compatibility, module structure, transport APIs, log strings, or tests that encode obsolete implementation details.

Preserve user-facing behavior only when it is useful and intentional. Data-safety semantics take precedence over compatibility.

The target remains:

```text
EntryStream -> Reconciler -> SyncOp -> Planner -> WorkItem -> Scheduler
                                      |
                                      +-> Local / Remote / Object endpoint capabilities
```

One binary (`sy`) acts as client and private remote agent (`sy __serve`). `sy-remote` must disappear before 0.5.

- bounded channels/backpressure;
- typed library errors and contextual application errors;
- no recoverable `unwrap()`/`expect()` in production paths;
- every unsafe block has a `// SAFETY:` invariant comment;
- run `cargo fmt --check` and `cargo clippy --all-features --all-targets -- -D warnings`;
- use `cargo deny`, audit, and Miri where relevant;
- when the CLI is replaced, use the `usage-rs` facade rather than building new clap infrastructure.

The branch remains Edition 2021 while substantial legacy code still compiles. Moving to Edition 2024 is reasonable after the legacy stack is deleted and should be an explicit reviewed migration, not opportunistic churn.

## Current 0.5 foundations

### Engine domain and ordered reconciliation

`src/engine/domain.rs` owns engine-native types independent of legacy `FileEntry`/`SyncTask`:

- canonical non-empty `RelativePath`;
- nanosecond `Timestamp`;
- opaque 32-byte `EntryIdentity` for scan/open/commit race detection;
- lean `Entry` and `EntryKind`;
- semantic `SyncOp` and `SkipReason`.

`src/engine/reconcile.rs` is the bounded ordered merge layer:

- at most one source and one destination entry are retained;
- it emits `SourceOnly`, `Matched`, and `DestinationOnly` relationships;
- source and destination streams must be strictly ordered;
- duplicate/out-of-order entries are rejected at the trust boundary.

Do not put transfer strategy, xattrs, ACLs, sparse extents, or block signatures into the base `Entry`.

### Semantic planning

`src/engine/planner.rs` decides what semantic change is required without choosing a byte-transfer mechanism. It supports quick, size-only, checksum, and always-changed comparison modes, plus update-only, ignore-existing, existing-only, and preservation policy.

Checksum mode deliberately returns `NeedContentComparison` when same-size files require content comparison. Remote v3 resolves that state during complete no-mutation preflight with explicit identity-checked whole-file BLAKE3 hashes; rolling signatures remain a separate delta-transfer mechanism.

Entry-kind changes become semantic `SyncOp::Replace`; transaction safety belongs to execution, not comparison policy.

### Disk-backed complete preflight

Remote v3 push no longer materializes a whole semantic plan in memory. A complete ordered source/destination reconciliation derives three disk-backed products before mutation:

```text
source EntryStream --\
                     +-> OrderedReconciler
remote EntryStream --/          |
                                +-> PlanJournal
                                +-> DeletePlan / reverse journal
                                +-> FinalizeJournal
```

`PlanJournal` preserves complete `SyncOp` records, native/non-UTF8 paths, identities, modes, timestamps, and symlink targets. Records are bounded to 1 MiB and validated while decoding.

Deletion is exact and bounded. `DeleteTracker` sees the full selected source namespace and complete destination scan, counts exact eligible/candidate entries, protects candidate parent directories containing source-backed or excluded descendants, and replays children before parents. Safety is represented by one typed `DeleteLimit`: unlimited, percentage, or absolute count. The limit is checked against the final protected candidate count during `DeleteTracker::finish()` before mutation; `force` bypasses the limit explicitly.

Directory final metadata is journaled separately and applied child-before-parent after main work and deletion. Parent metadata is finalized even when initially equal because descendant namespace mutation changes directory timestamps.

Execution order is a hard invariant:

```text
complete preflight
  -> main semantic work
  -> wait for all main workers
  -> reverse delete replay
  -> reverse directory metadata finalization
```

### Selection safety

Source selection and deletion scope are intentionally separate.

`preflight_remote_push_scoped` allows semantic work to be narrowed without making a source entry disappear from deletion protection. The destination scan remains complete/unfiltered; destination-side selection is expressed through `delete_in_scope` instead of hiding entries from reconciliation.

This is the boundary to preserve for every future selector. In particular, never implement source gitignore semantics by simply enabling gitignore filtering on the destination scan.

### Remote v3 runtime and transport

Supported local -> SSH pushes now use protocol v3 end to end rather than old `StreamingSync` v2.

The active v3 path includes:

- external OpenSSH transport;
- same-binary `sy __serve` remote agent;
- protocol handshake/capability negotiation and session/root open;
- descriptor/root-handle-backed remote filesystem authority;
- bounded multiplexed request routing;
- ordered remote metadata scan;
- cloneable scheduler-facing request handle;
- adaptive rolling-signature streams for delta candidates;
- staged whole/delta file reconstruction;
- metadata and namespace mutation RPCs;
- bounded scheduler/controller fan-out.

OpenSSH startup uses batch mode and restores useful stderr context on failure. The remote runtime holds session-root authority rather than reopening a lexical root pathname for every request.

The router must flush every frame it reports as written. `tokio::io::stdout()` wraps `std::io::Stdout`, a LineWriter that holds newlineless binary frames until a newline or a full 1 KiB buffer; Entry payloads contain `0x0a` only where a hash/mtime byte happens to be one, so Ack-only flushing deadlocked every real stdio session (scan stall mid-frame, EntryEnd never delivered, both sides parked). `tests/remote_stdio.rs` drives a spawned `sy __serve` child over real pipes and fails by timeout without the per-frame flush; in-memory `tokio::io::duplex` tests cannot catch this class. Related known defect: on clean stdin EOF the agent reports early-eof as an I/O error and exits 1 instead of exiting zero.

### Remote transfer execution

`RemotePushExecutor` selects whole-vs-delta transfer at execution time under scheduler admission. Independent leaf work is bounded-concurrent; directory creation is awaited in preorder so descendants never race their parent.

Transfer slot ownership lasts through completion, and publication/handoff liveness has Loom coverage. File reconstruction is staged and final file mode handling is deferred appropriately.

Ignored completion states are explicit: only a resume hit is accepted as a completed transfer; an already-active file is surfaced as contention rather than silently treated as success.

### V3 push semantics already routed

The top-level local -> SSH push adapter currently supports v3 for ordinary configurations including:

- default quick comparison;
- `--ignore-times`;
- `--size-only`;
- `--checksum`;
- update-only;
- ignore-existing;
- existing-only;
- ordinary include/exclude filters;
- `--dirs` shallow selection;
- `--exclude-vcs` / `.git` exclusion;
- `--gitignore` selection with source-derived deletion scope (see `engine::ignore_scope`; walker/scope parity is proptest-pinned, and ignored destination-only entries are protected rather than deleted, matching rsync's protect-by-default `--delete` semantics);
- `--dry-run` previews, and `--diff` per-operation dry-run detail including delete-journal lines and `bytes_would_add`/`bytes_would_change` accounting (commit 323a598 also fixed the local 0.5 engine, whose planned-task path had never recorded byte accounting at all; `--diff` without `--dry-run` is now rejected at validation);
- `--bwlimit` pacing (commit d7cc49e): the router writer meters outbound `Data` payload bytes with a shared one-second-burst token bucket while control frames bypass the limiter; the local engine bypasses kernel fast paths when a limit is set and paces the staged streaming copy per chunk (previously the limit was silently ignored on every non-streaming path);
- min/max-size semantic selection;
- preserve permissions;
- preserve times;
- normal symlink preservation;
- percentage and absolute-count delete limits, including `0` unlimited semantics, plus force;
- bounded parallel transfer scheduling;
- dry-run preview.

Dry-run consumes the exact same completed preflight plan but never constructs or runs `RemotePushExecutor`. It reports semantic create/update/skip counts, exact delete candidates, and source-byte estimates for creates/updates. Runtime coverage requires the server to observe only preflight-safe requests; file, mutation, and metadata RPCs during dry-run are test failures.

Absolute delete-count runtime coverage proves both sides of the boundary: an over-limit plan is rejected after the complete destination scan with no mutation-capable request and an unchanged destination, while a count equal to the final candidate set allows those deletions.

`diff_mode` is mapped (commit 323a598): the v3 preview yields one `PreviewOp` per planned operation plus one per delete-candidate replay action, and the adapter emits the legacy line formats from that stream. The local 0.5 engine mirrors the same lines and byte accounting in `record_planned_task`; before that commit the local dry-run path never recorded `bytes_would_add`/`bytes_would_change` at all.

### Local compatibility path

Local sync still dispatches through `src/sync/reconcile.rs`, which adapts the new ordered engine semantics to the legacy task executor. It is compatibility scaffolding, not an API to stabilize.

Its useful safety work includes exact disk-backed delete preflight and atomic file/symlink replacement. It now uses the same typed deletion-limit contract as the engine, and protected candidate parent directories are removed from the safety count when replay will not delete them. Local execution still needs to move wholly under the new engine/executor architecture before 0.5 is complete.

## Protocol v3

Protocol v3 lives separately under `src/protocol/`; do not evolve `streaming/protocol.rs` into it.

Implemented protocol/runtime foundations include:

- typed `ProtocolError`;
- fixed 12-byte frame header;
- hard 1 MiB frame payload bound validated before allocation;
- typed frame kinds/flags and stream IDs;
- version-range negotiation;
- capability bitset including BLAKE3 and rolling signatures;
- client/server build and platform identity;
- component-framed native path encoding;
- ordered scan request/entry stream;
- rolling signature request/stream;
- file transfer, metadata, and mutation streams;
- adversarial/truncation/property tests;
- panic-free production frame decoder.

Relative paths are delimiter-free component sequences, not slash-delimited strings. Unix byte names and Windows UTF-16LE names must not share fake separator-byte semantics.

### Checksum comparison boundary

The existing signature protocol is not a whole-file checksum API. It emits adaptive per-block weak checksums and truncated BLAKE3 strong signatures plus final size/count/identity. Do not concatenate or reinterpret these as canonical content hashes.

Protocol v3 now has an explicit bounded whole-file BLAKE3 content-hash request/result using the negotiated BLAKE3 capability. Both local source and remote destination hashing validate the scanned identity while opening/reading, stream without whole-file buffering, and feed equality into `finish_content_comparison` before preflight can return. Dry-run performs the same hash preflight but emits no mutation request.

### Delete-limit contract

Deletion safety no longer carries a raw `max_delete` string alongside percentage-only engine state. The shared contract is:

```text
DeleteLimit::Unlimited
DeleteLimit::Percentage(u8)
DeleteLimit::Count(u64)
```

CLI parsing is explicit:

- bare `0` means unlimited;
- `0%` means zero percent, so any non-forced deletion is rejected;
- `N%` must be within 0..=100;
- a nonzero bare integer is an absolute final-candidate count.

`--force-delete` bypasses the configured limit. Both local ordered preflight and remote v3 enforce the same policy against the final replayable/protected candidate count before mutation. The legacy streaming boundary serializes this typed value only where its old string protocol still requires one.

Bidirectional sync still exposes only a percentage safety field internally. Absolute counts with `--bidirectional` are therefore rejected explicitly instead of being silently converted to 100%; do not change that until bisync itself has a coherent count-limit model.

## Current explicit v3 fallbacks

The adapter intentionally falls back for semantics that are not yet represented correctly:

- resume-only control flow and legacy directory cache;
- verification/checksum-database options;
- xattrs, hardlinks, ACLs, BSD flags, group/owner/devices/keep-dirlinks;
- non-preserving symlink modes;
- remove-source-files;
- backups and legacy partial-file behavior;
- CLI timeout overrides;
- compression policy/level;
- itemized output, progress, JSON events, and perf metrics;
- custom max-error policy.

Do not migrate these mechanically. Audit whether each behavior belongs in 0.5 and how it fits the new capability/transaction model.

## Known problems to eliminate

### Split execution architecture

Supported local -> SSH pushes are now v3, but local sync and unsupported remote configurations still use compatibility/legacy paths. 0.5 is not done until one engine/execution architecture owns local and remote behavior and fallback-only legacy stacks are deleted.

### Legacy stacks

Before release, delete or replace:

- `src/bin/sy-remote.rs` if still present;
- old `src/transport/`;
- old `src/streaming/` v2;
- old `SyncEngine<T: Transport>` in `src/sync/mod.rs`;
- old `StrategyPlanner` in `src/sync/strategy.rs`;
- remaining embedded ssh2 connection stack after all call sites use external OpenSSH;
- compatibility whole-tree APIs and duplicate planners/stats/transfer types.

Do not add new features to v2 to ease migration.

### Scanner metadata cost

The final endpoint scanner should request only metadata required by active policy. Hardlink identity, sparse extents, xattrs, ACLs, flags, and hashes should remain demand-driven.

### Directory transactions

Directory <-> non-directory replacement remains intentionally rejected. It needs an explicit tree transaction/tombstone rollback design rather than recursive destructive replacement.

### Source/destination races

Identity is now present in the v3 scan/transfer model, but every destructive or content-comparison path must continue tightening scan/open/commit race validation. Delete replay should ultimately validate destination identity tokens as well as paths so a concurrently replaced path cannot be removed after preflight.

### Name/collision semantics

Cross-platform sessions must preflight destination namespace semantics. Case-insensitive or normalization-insensitive destinations can collapse distinct source names. Detect collisions before mutation; never silently rename or overwrite one source entry with another.

### Root confinement

The v3 remote runtime is descriptor/root-handle based, but confinement remains a security invariant to preserve across every new endpoint operation. Linux should use `openat2`/`RESOLVE_BENEATH` where available; macOS/other Unix should use no-follow directory-FD walking rather than lexical normalization as the security boundary.

## Scheduler

The scheduler already owns resource admission and bounded active-file execution, but a file-count budget is not the final resource model. Evolve budgets based on evidence to account for:

- active files;
- buffered/in-flight bytes;
- metadata concurrency;
- hashing/compression CPU;
- network frame/write pressure.

A large transfer should consume more byte budget than a tiny file even if both count as one active file.

## Remote bootstrap / issue #26

Issue #26 asks for statically linked musl releases. Do not respond unless the user explicitly asks later.

The request fits the current architecture:

- one static `sy` binary can be copied to a remote and invoked as `sy __serve`;
- no separate `sy-remote` artifact;
- external OpenSSH avoids maintaining a second SSH implementation;
- target at least x86_64 and aarch64 Linux musl artifacts;
- release CI must verify the result is truly static.

Automatic bootstrap can follow protocol stabilization: try an installed compatible `sy`, then upload/cache a trusted matching static agent only if needed.

## CLI direction

Retain familiar rsync-like syntax where useful, but remove misleading/redundant flags rather than carrying permanent compatibility debt.
